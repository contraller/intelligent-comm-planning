# 外包对接问题回复

整理日期：2026-10-08。依据为本次沟通记录、用户提供的截图及现有项目资料。本文用于协作沟通，不替代合同、甲方批准的需求文件或验收文件。

## 1. 前端与后台业务系统的责任边界

需求文档描述的是完整系统，包含监控中心、工作台、资源管理、系统管理和算法相关页面。界面、地图交互、表单校验、算法任务提交及结果展示属于前端工作；数据持久化、账号权限、资源增删改查接口、日志和业务流程需要业务后端提供支持。

因此，“包含后台管理系统”可以用于描述功能范围，但不能直接推导出外包方已经承诺承担业务后端开发。建议按以下三部分确认责任：

| 部分 | 工作内容 | 当前口径 |
|---|---|---|
| 前端界面 | 各模块页面、地图及图层、表单、图表、任务状态与结果展示 | 外包方负责；采用 Vue 3 + TypeScript |
| 业务后端 | 登录权限、账号管理、台账增删改查、数据库读写、日志、业务流程及算法调用衔接 | 承担方及具体功能范围待双方书面确认 |
| Python 算法服务 | 网络规划、传播与覆盖计算、故障诊断及约定的算法结果接口 | 实验室负责；具体范围按批准需求和接口清单执行 |

建议由业务后端统一处理登录权限、业务数据和算法任务衔接，调用实验室提供的 Python 接口。最终是否由浏览器直接访问算法服务，应在联调前统一确认鉴权、任务关联和结果保存方式。

现有模块分工文件仍将资源管理数据层列为我方职责，不能未经确认将全部增删改查和数据库工作转给外包方。建议逐模块列出“页面、业务接口、数据库、算法、部署联调”的负责人后冻结分工。

## 2. 开发规范与交付物

截图中已经明确：前端采用 Vue 3 + TypeScript；需求规格说明书使用 v4；软件设计说明由项目侧提供初稿，各开发方按实际实现补充、修订。

已明确的整体交付物如下。它们是整个项目的交付清单，各方只对自身承担部分负责，由项目侧汇总。

| 交付物 | 应包含的内容 |
|---|---|
| 前后端源代码 | 前端、业务后端、Python 算法服务的实际项目源代码 |
| 可执行程序 | 在目标环境可部署运行的程序或发布包；具体包装形式待确认 |
| 数据库文件 | 按最终选定数据库提供建库、表结构和初始化数据；交付形式待确认 |

| 软件设计说明 | 项目侧初稿及各开发方对实际模块、接口、数据和部署设计的修订 |
| 用户手册 | 按最终交付界面和操作流程编写 |
| 研制总结报告 | 由项目侧汇总，各方提供自身开发、测试和实施情况 |

目前尚未收到可据以确认的完整开发标准清单。甲方仍需确认：标准名称及版本、文档模板、测试与验收方式、安装包和数据库文件格式，以及是否有第三方组件源码或离线依赖交付要求。不能把建议的工程做法表述为甲方已经确定的标准。

建议随源码交付构建说明、依赖及版本清单，随程序交付安装部署说明，并提供与接口定义匹配的联调样例；这些为建议补充项，是否作为正式交付物需确认。

## 3. 离线 GIS 底图与地图服务

已知已有一份离线地图数据，但还需检查其格式、坐标系、覆盖范围、缩放级别及使用授权，才能确定服务方式。

- 如果已经是按层级组织的栅格瓦片目录，可通过内网 HTTP 静态服务提供瓦片地址供前端调用。
- 如果是 MBTiles、矢量瓦片或其他打包格式，需要相应的瓦片读取和发布服务。
- 如果是原始影像、DEM 或其他 GIS 原始数据，应先处理、发布为前端地图组件可读取的图层或服务。

仓库中已整理的 DEM、地物网格和道路数据主要供算法使用，不能据此认定离线底图瓦片服务已经完成。地图数据已具备与地图服务已可调用是两个不同的交付状态。

实验室可提供已有地理数据及算法结果图层定义；底图服务由谁部署、由谁维护和服务地址由谁提供，仍需明确负责人。建议先用一份实际数据完成前端加载验证，再冻结地图框架和服务协议。

## 4. 系统集成测试环境

需要提供双方可访问的联调环境。建议由项目侧协调学校服务器或私有云，并提供经批准的远程访问方式；是否通过 VPN 接入由学校网络条件决定。目前尚不能确认学校服务器或 VPN 已可用。

联调环境需要容纳前端、业务后端、Python 算法服务、数据库及离线地图服务，并明确部署权限、访问地址、端口、运维负责人和问题处理渠道。

如学校环境暂不能提供，公有云可以作为候选联调方案，但需先确认费用承担及拟放入的数据是否允许上云。平台资料未经确认时可先使用合成样例数据进行开发联调。

最终部署操作系统已确定为麒麟。开发联调环境与最终验收环境可以分阶段安排，但验收前必须在实际麒麟环境及目标硬件上完成运行验证；CPU 架构、数据库和浏览器版本应尽早补齐。
