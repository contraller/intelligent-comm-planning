## 1. 通用约定

### 1.1 基础信息

| 项 | 值 |
|---|---|
| 协议 | HTTP/1.1，`Content-Type: application/json; charset=utf-8` |
| Base URL | `http://<host>:<port>/api/v1` |
| 编码 | 一律 UTF-8，请求与响应均不做额外转义 |
| 时间 | ISO 8601 带时区，见数据字典 0.5 |
| 坐标 | EPSG:4326，`[lon, lat]` 顺序 |

### 1.2 统一响应包络

业务 JSON 接口以 `code`、`message`、`data` 为基础包络；文件下载接口返回二进制内容：

```json
{
  "code": 0,
  "message": "success",
  "data": { },
  "request_id": "req-20260908-0001"
}
```

- `code = 0` 表示成功，非 0 表示失败；失败时 `data` 可以为 `null`，也可以包含字段校验问题或业务建议
- `request_id` 在支持请求回执的接口中返回；未接入回执的只读接口及框架级错误响应不包含该字段
- **HTTP 状态码只表达传输层语义**（200/202/4xx/5xx），业务成败一律看 `code`。前端不要依据 HTTP 200 判断业务成功

`/api/v1` 路由的框架级参数校验错误返回 HTTP 422 / `code=1001`，`data` 为字段问题列表；资源接口主动抛出的错误同样返回业务包络，不再返回单独的 `detail`。无效地图 `bbox` 返回 HTTP 422 / `1001`，资源版本过期返回 HTTP 409 / `1205`；缺失资源对象返回 HTTP 404 / `1002`。未定义路径或方法仍由 HTTP 状态区分。未加 `/api/v1` 前缀的健康检查保持既有错误格式。

### 1.3 错误码

| code | 含义 | 前端建议处理 |
|---|---|---|
| 0 | 成功 | |
| 1001 | 参数缺失或格式错误 | 表单标红，`message` 指明字段 |
| 1002 | 引用的实体不存在（node_id / link_id 等） | 提示数据不一致，建议刷新 |
| 1003 | 枚举值非法 | 前端自查，属于对接缺陷 |
| 2001 | 任务不存在或已过期 | 结果保留 24h，超时提示重新计算 |
| 2002 | 任务仍在计算中 | 继续轮询 |
| 2003 | 任务计算失败 | 展示 `data.error_detail` |
| 3001 | 约束过严，无可行解 | **展示 `data.suggestions` 中的放宽建议**（SR-4.2.1.1、SR-4.2.4 扩展流要求） |
| 3002 | 频率资源不足 | 展示 `data.gap` 频率缺口统计（SR-4.2.2.2 扩展流要求） |
| 3003 | 故障对象与故障类型不适配 | 阻止保存并提示（SR-5.1 扩展流要求） |
| 4001 | 知识图谱无匹配结果 | 展示 `data.similar` 相似知识推荐（SR-6 扩展流要求） |
| 5001 | 服务内部错误 | 提示稍后重试 |

> 3001 / 3002 / 4001 这三个不是"错误"，是软需明确要求要**带建议返回**的业务分支。前端必须渲染 `data` 里的建议内容，不能只弹一句"失败"。

### 1.4 异步任务模式（SR-4.2 g 强制要求）

所有**规划与分析类计算**一律异步。规则：

```
POST  /plan/xxx           提交任务  → HTTP 202 + { task_id, estimated_sec }
GET   /tasks/{task_id}    查询进度  → { status, progress, stage }
GET   /tasks/{task_id}/result   取结果 → 各接口自有结构
POST  回调（可选）         算完主动推 → 前端提供 callback_url
```

任务状态机：

```
PENDING → RUNNING → SUCCESS
                  ↘ FAILED
                  ↘ CANCELLED
```

**`GET /tasks/{task_id}`**

```json
{
  "code": 0,
  "data": {
    "task_id": "tsk-20260908-0007",
    "task_type": "DEPLOYMENT_PLAN",
    "status": "RUNNING",
    "progress": 0.62,
    "stage": "正在评估候选点覆盖增益 (312/500)",
    "submit_time": "2026-09-08T14:30:00+08:00",
    "estimated_remain_sec": 45,
    "error_detail": null
  }
}
```

- `progress` 为 0–1 浮点，`stage` 是可直接展示的中文进度描述
- **建议轮询间隔 2 s**，前端不要低于 1 s
- 结果保留 **24 小时**
- `DELETE /tasks/{task_id}` 取消任务

> 软需 SR-4.2 g 明确写了"响应时间指标仅适用于参数录入、方案查看等界面交互操作，不含算法计算耗时"。这条要在验收时用上：**规划计算耗时不受 2 秒响应时间指标约束**，但界面交互类接口受约束。

## 2. SR-4.2 无线网络规划接口

### 2.0 规划页 DEM 底图版本（2026-10-21 增量）

正式规划页沿用 `GET /api/v1/resource/context?context=planning`，其 `data` 增加当前 DEM 的只读元数据：

```json
{
  "terrain": {
    "source_sha256": "a42f42e17d38218f539cb04323696cacb296c4bcc11bb50a77cccf927f91bf7f",
    "bbox": [113.14986111114996, 36.27597222221908, 114.9498611111502, 37.72402777777483],
    "source": "太行山东麓_20261009.zip / dem/dem_taihang.tif"
  }
}
```

`bbox` 使用 EPSG:4326，顺序为 `[最小经度, 最小纬度, 最大经度, 最大纬度]`。前端应将 `source_sha256` 和 `bbox` 与已打包的 `maps/sr4-terrain.json` 核对；不一致时不显示 DEM 图像，但仍显示资源、规划站点和链路。该字段不改变资源表 `revision`，也不是覆盖计算结果；覆盖图仍以规划结果中的 `coverage` 为准。

2026-10-22 新版规划页增量：`front_design/radio-planning-20261022` 保留并校验 `terrain` DTO（缺失时为未知），地形加载器同时验证 CRS、源哈希、范围与实际 PNG 字节的 SHA-256，校验通过后创建临时图片地址。地形位于业务图层下方；加载失败不隐藏点线，换版/离页取消请求并释放图片地址。2026-10-23 已扩展至 GIS 与诊断，诊断额外核对冻结方案的 DEM 指纹；规划/诊断默认关闭道路，GIS 可选道路仅显示与 DEM 重叠范围，不平移瓦片坐标。

### 2.0.1 新版 GIS 资源目录与展示资料（2026-10-23）

#### 资源数据库模式（0014 增量）

新版交付入口 `scripts/serve_delivery.py` 固定设置 `RESOURCE_DATASET_MODE=database`，先校验资源已初始化再提供服务。
直接启动开发后端时也须显式设置该环境变量；未设置时保留历史算法的 `file` 来源模式，但不是新版交付入口的降级路径。
两种模式不混读：数据库模式的资源目录、分页、详情、频点、预设和任务引用校验读取同一数据库版本，不再逐次读取原 CSV。
同一 HTTP 请求固定一次资源快照，SR4 提交时另取该版本完整输入副本传入工作线程，基础规划和父方案重算均禁止对缺失表回退文件。

新增表 `resource_dataset_versions` 保存 `revision/content_hash/source/data_origin/snapshot/created_at`；
`resource_dataset_current` 保存项目作用域的生效版本指针。快照为不可变 JSON，包含 10 张输入表及各原文件相对路径、SHA-256 和来源时间；0014 只建立底座，0015 的单设备保存见 2.0.2。
首次显式初始化沿用原六类资源文件字节摘要生成的业务版本，因此相同资料不使现有任务或方案失效。
整包另有独立 SHA-256 校验。重复初始化只回读已有版本，禁止用当前文件覆盖库内资料。

现有接口请求/成功响应字段保持不变，构造数据标识继续保留。新增失败分支沿用 `code/message/data`：
未配置数据库或模式非法为 HTTP 503 / `5001`；未迁移、连接失败、快照损坏或来源结构无效为 503 / `5002`；
资源尚未初始化为 503 / `5003`；提交资源版本已变化仍为 409 / `1205`。错误不返回旧 CSV 结果。
数据库迁移与初始化须由操作者分别执行，启动不自动建表、导入或重置。DEM/地物栅格仍沿用已有指纹校验，不纳入本次资源表迁移。

- `GET /api/v1/resource/gis-directory?context=gis&revision=<resource-version>`：完整轻目录，供资源树按节点、设备、型号和干扰源分组；不代替对象详情。
- `GET /api/v1/resource/gis-scene?context=gis&revision=<resource-version>`：同版完整资源展示投影；不从任意任务挑选“最新规划”充当当前网络。

两接口沿用 `code/message/data` 包络，要求显式联调模式和 `situation.view`；`context` 默认 `gis`，只接受该值，`revision` 必填。参数错误 422/1001、版本不一致或读取中换版 409/1205、未启用联调 401/1101、无权限 403/1104。接口只读，不建表、不生成作业。

共同数据为 `revision/context/dataOrigin/source/updatedAt/nodes/devices/models/interferences`，`dataOrigin=SYNTHETIC_INTEGRATION`，来源明确为项目构造基线、非生产/非实测。对象字段复用现有资源读取 DTO；目录设备仅返回 `device_id/node_id/model_id/status/alert/availability/origin`，型号仅返回 `model_id/model_name/device_class`。展示资料返回完整对象及 `snapshotId=GIS-RES-<revision>`、`networkState=missing`、`networkMessage`。未关联规划方案时不虚构链路、路由、覆盖或实时观测。

前端严格校验版本、唯一 ID、设备与节点/型号关联、设备坐标与所属节点一致。自动视口读取去重，显式刷新仍重新查询；后台地图读取不反复插入整页“正在读取”提示。任务库整行和“打开”按钮共用既有详情接口，成功回显已打开消息；取消放弃草稿不读取另一任务。

固定联调身份仅在 `FRONTEND_INTEGRATION_DEMO=1` 下由 `/api/v1/auth/session` 返回，本批权限为 `planning.view`、`planning.execute`、`planning.save`、`planning.confirm`、`resources.view`、`situation.view`；不包含重置、系统管理或 SR5/SR6 写权限。权限版本为 `integration-identity-v2`，会话代次为 `integration-session-v2`，旧页面需重新加载并获取身份。此身份不是正式账户鉴权，保存与确认仍执行现有版本、来源和硬约束校验，不能使参考方案绕过确认限制。

### 2.0.2 新版台账单设备参数维护（0015，2026-10-23）

只维护数据库中已有设备的基础参数，不表示向真实设备下发配置。两接口只在显式联调模式开放，要求 `resources.view` 和 `resources.device.edit`；后者仅授予联调编辑者，不授予规划员或审核者，也不等同 `resources.edit` 的整库维护权限。

**读取：`GET /api/v1/resource/maintenance-context`**

查询必填 `context=ledger`、`revision`、`device_id`。拒绝重复参数、未知参数、批量 ID、GIS 上下文及旧版本。成功包络的 `data` 为：

- `revision`、`base_revision`：同一当前资源版本。
- `device`：现有设备详情线协议 DTO，包含 `device_id/node_id/model_id/antenna_id` 及基础参数；不返回整库。
- `stations/models/antennas`：仅该设备关联的节点、型号、天线各一条；型号上下限为数字，前端据此显示约束，不自行猜测。
- `impact.plan_ids/link_ids/description`：依赖此资源版本的已保存方案编号；当前未计算链路级影响，`link_ids=[]` 不代表零影响，`description` 明确说明缺失及全局版本失效规则。

**保存：`POST /api/v1/resource/changes`**

使用当前 Cookie，另带 `X-Session-Id`、`X-CSRF-Token`；身份来自服务端，不接受请求体传操作者。示例：

```json
{
  "context": "ledger",
  "base_revision": "resource-e4a642d6ea91744b",
  "request_id": "device-edit-unique-id",
  "stations": [],
  "devices": [{"id": "DV-0001", "antenna_height_m": 17.1, "tx_power_dbm": 51.76, "work_freq_khz": null}]
}
```

`devices` 必须恰好一条，编号不可更改；三个参数至少提供一个。`stations` 可省略或为空；其余资源字段、模式、端口、归属、型号、状态、上下架、恢复标识及未知字段全部拒绝。
挂高为不小于 0 的有限数字；功率为不超过型号上限的有限 dBm；频率为型号范围内的正数 kHz 或显式 `null`。不接收布尔值、数字字符串、NaN 或 Infinity。未提交频率表示保留，显式 `null` 表示清空，幂等摘要区分两者。
来源功率因既有舍入超限不超过 0.040001 dB 时，仅原样保留并返回警告；新的超限功率拒绝，不扩大型号限制。

成功 HTTP 200，`data` 为 `object_id/changed/revision/read_revision/device/affected_ids/warnings`；`device` 为保存后的设备 DTO；警告项为 `object_id/field/message`。前端映射为既有 camelCase `ResourceMutationReceipt`，不把分页结果拼成整库。

- 新版本快照、当前指针和 `resource_dataset_operations` 回执同事务保存，条件锁拒绝旧版本覆盖；失败不保留半个版本。
- 相同身份、请求编号及内容重放原回执，先查回执再检查旧基础版本；同编号换内容或身份为冲突，不自动重发新请求。
- 无实际差异返回 `changed=false` 及原版本，但仍保存回执；改回原值也产生新版本，不重新认证旧方案。历史快照与回执不允许覆写或删除。
- 新版本只改变指定设备参数；原文件与来源 SHA-256 清单保留，新快照记录父版本、操作者、请求标识及提交时间。
- 保存后新版台账刷新；GIS 再读取时使用同版资源。旧方案保留历史，但来源变化后需重新保存任务并运行 SR4；在途计算保留已冻结的输入，不自动改参数、重算或确认方案。基础资源值不等同优化结果的强制固定参数。

错误：422/`1001` 参数或范围无效；404/`1002` 设备不存在；409/`1205` 资源版本变化；409/`1206` 请求标识复用冲突；401/`1101` 未启用联调；403/`1104` 无权限；403/`1105` CSRF 拒绝；409/`1106` 会话变化；503/`5001` 数据库配置缺失；503/`5002` 数据库、迁移或快照失败；503/`5003` 未初始化或非数据库模式。不降级写 CSV，不把失败当成功。

### 2.0.3 新版台账设备上下架（2026-10-23）

本接口维护资源生命周期，不表示故障、离线、设备关机或实际配置下发。沿用 0015 的资源版本及操作回执表，不新增数据库表。显式联调模式下要求 `resources.view`、`resources.device.availability`；专项写权限仅给联调编辑者，不赋予整库编辑、参数编辑或正式账户权限。两个 POST 均携带 Cookie、`X-Session-Id`、`X-CSRF-Token`。

**预览：`POST /api/v1/resource/device-availability/preview`**

```json
{"context":"ledger","revision":"resource-f82ea3157ad8d95b","ids":["DV-0001","DV-0002"]}
```

`ids` 为 1–50 个不同的现有设备编号；请求中的身份、状态、其他字段及 GIS 上下文全部拒绝。成功返回 `revision/base_revision/selected_ids/device/stations/models/antennas/impact`。`selected_ids` 回显核验清单，`device=null`、三个字典数组为空，因为这是批量确认而非设备编辑表单。`impact.plan_ids` 列出同资源版本的已保存方案，`link_ids=[]` 明确表示未提供链路级影响，不能显示为“零影响”。预览不写资源或回执，取消不提交上下架。

**提交：`POST /api/v1/resource/device-availability`**

```json
{"context":"ledger","base_revision":"resource-f82ea3157ad8d95b","request_id":"availability-unique-id","ids":["DV-0001","DV-0002"],"availability":"OFF_SHELF"}
```

`availability` 只接受 `ACTIVE`、`OFF_SHELF`；清单限制同预览，拒绝布尔值、数字编号、重复编号和未知字段。`request_id` 必填。身份由会话确定；不能用参数保存接口旁路改上下架。

成功包络 HTTP 200，`data` 包含：

| 字段 | 含义 |
|---|---|
| `object_id` | 固定为 `resource-device-availability` |
| `changed` | 是否存在实际状态变化 |
| `revision/read_revision` | 同一结果资源版本 |
| `updated/unchanged` | 将请求编号完整、互斥地分组；不遗漏、不混入其他设备 |
| `affected_ids` | 与 `updated` 相同的编号集合 |
| `warnings` | 本版本为空数组 |

整批核验、快照、当前指针和回执同事务保存；任一编号不存在或版本变化时整批拒绝。摘要将设备清单按集合规范化，顺序不同可重放同一请求；同标识换内容、目标状态或操作者返回冲突。幂等检查在当前版本校验之前，迟到的旧请求只返回原回执，不再次切回旧状态。
全部无变化时仍记录回执，但 `changed=false`、资源版本不变。重新启用实际改变状态时生成新版本，即使有效配置回到原值也不能重新认证旧方案。

读取规则同步到 `/resource/context`、设备分页/详情和 GIS 目录/场景：统计返回真实 `active/off_shelf`；设备分页接受 `availability=ACTIVE|OFF_SHELF|UNKNOWN`，在全库过滤后分页并返回对应 `total`。旧构造行缺少生命周期字段按原在架基线解释，显式非法值拒绝；不是把缺失设备运行状态补成正常。原 `status/alert` 不随上下架改变。

规划规则：

- 新任务校验、保存和提交均拒绝明确指定的下架端点、全部设备已下架的任务参与节点，以及已无在架设备的指定频段。
- 任务内容不变但资源换版时，重新保存生成新的输入版本，保留相同条件版本；不得继续绑定旧资源。
- SR4 保留完整冻结输入作审计，实际部署、设备绑定和代表型号选择只使用在架设备。既有候选中继规划仍按原算法执行，不把下架物理设备重新绑定或伪称启用。
- 固定父拓扑包含下架设备时明确失败，不能静默替换设备。资源变化后旧方案保留为历史，确认和继续使用仍按既有来源校验拒绝；启用不会自动重算、转正或恢复旧方案有效性。
- 已受理的在途作业继续用原冻结版本，不修改其输入或自动取消。

错误沿用 2.0.2：422/`1001` 非法请求、404/`1002` 设备缺失、409/`1205` 资源变化、409/`1206` 请求复用冲突，以及既有鉴权/CSRF/数据库失败。资源分页非法上下架枚举返回 422/`1001`。前端保留错误和当前选择；明确拒绝与结果未知分开显示，未知结果重试原请求，不自动创建新事务。

### 2.8 方案管理

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/plans` | 保存已完成作业的方案版本 |
| GET | `/plans?context=planning&task_id=TS-0001&page=1&page_size=10` | 版本化方案列表 |
| GET | `/plans/{plan_id}?context=planning&task_id=TS-0001` | 版本化方案详情（部署+路由+频率+参数+指标） |
| POST | `/plans/compare` | 多方案横向对比，body 传 `solution_ids[]` |
| POST | `/plans/{plan_id}/confirm` | 确认版本化方案并设为任务当前方案 |
| GET | `/plans/{plan_id}/export?context=planning&task_id=TS-0001&format=json\|xlsx` | 版本化方案导出 |

`POST /plans` 请求须包含 `context`、`request_id`、`task_id`、`expected_revision`、`job_id`、`name` 和 `note`。服务端只保存归属当前任务且状态为 `SUCCESS` 的完整作业结果；达标结果状态为 `SAVED`，未达标或来源资源已变化的结果状态为 `REFERENCE`。相同请求编号与内容幂等返回，同一作业当前只允许保存一次。保存内容包括冻结任务输入、节点、设备、链路、主备路由、频率、电台参数、指标、校验项和约束缺口。

带 `task_id` 的列表和详情读取数据库中的版本化方案，并返回前端 `ApiPlan` 契约；不带 `task_id` 时仍读取 `data/runtime/plans/` 下的旧算法方案，供既有算法接口兼容。

版本化确认请求包含 `context=planning`、`request_id`、`task_id` 和 `expected_revision`。服务端校验方案归属、输入版本和当前资源版本，只允许 `SAVED` 方案首次确认；成功后返回完整 `ApiPlan`，其中 `state=CONFIRMED`、`current=true`、`confirmed_at` 非空。同一任务只保留一个当前方案指针，原确认方案仍为历史 `CONFIRMED`，但回读时 `current=false`。相同请求编号与内容幂等返回；请求编号复用、版本不一致、资源变化和不可确认状态分别返回明确错误。`REFERENCE` 方案返回 `3001`，不会被转正。不带请求体的 `/api/v1/plans/{solution_id}/confirm` 仍按旧算法文件规则执行。

版本化对比请求包含 `context=planning`、`task_id` 和 2–4 个不同的 `solution_ids`。所有方案须归属同一任务，并具有相同的冻结任务条件版本和资源版本；响应按请求编号顺序返回完整 `ApiPlan` 数组。方案状态不限制为可确认状态，`REFERENCE` 可用于分析约束缺口。只传旧格式 `solution_ids` 时仍返回旧算法指标摘要；旧格式要求非空字符串编号列表，缺失、空列表或错误类型返回 HTTP 422 / `1001`。

版本化导出请求包含 `context=planning`、`task_id` 和 `format=json|xlsx`。JSON 返回标准接口包络中的完整 `ApiPlan`，现有前端据此生成本地 JSON/XLSX 文件；XLSX 直接返回服务端二进制工作簿。两种格式均从 `planning_plans` 的冻结快照生成，不读取算法运行文件。无 `context` 和 `task_id` 时仍使用旧算法方案导出，继续支持 `json`、`csv` 和 `xlsx`。

## 3. SR-5 故障诊断接口

### 3.0 正式规划方案来源（2026-10-20 增量）

正式请求须显式传 `context=planning`，与下文旧文件方案和合成基线示例区分。`GET /api/v1/fault/plan-sources?task_id={task_id}` 返回该任务当前可用于诊断的数据库方案；成功时 `data.items` 至多一项，包含 `task_id`、`plan_id`、`revision`、`resource_revision`、`name`、`version`、`state`。没有当前方案、资源已变化或冻结拓扑不完整时返回空列表及 `data.reason`，不得默认选择合成基线。

正式诊断仍调用 `POST /api/v1/fault/diagnose`，请求示例：

```json
{"context":"planning","request_id":"diagnose-001","task_id":"TS-0001","plan_id":"PLAN-0001","scenario_id":"FS-0001","scenario_version_id":"FSV-0001"}
```

正式诊断必须明确传 `plan_id`、`scenario_id` 和 `scenario_version_id`，仅接受同任务、当前 `CONFIRMED` 且资源版本未变化的方案，以及与该方案版本绑定的未归档场景版本。所选方案须含节点、设备绑定、链路、主备路由及通联需求的冻结快照；缺失时返回 `1203`，资源变化返回 `1205`，无当前方案返回 `2001`。场景中的故障对象须存在于该方案快照中，不存在返回 `1002`。接口返回异步 `task_id`，通过 `GET /api/v1/fault/tasks/{task_id}` 轮询；诊断结果标识 `context`、`network_solution_id`（即数据库 `plan_id`）、`network_task_id`、`network_revision`、`network_resource_revision`、`scenario_version_id` 和 `scenario_version_no`。

影响分析仍调用 `POST /api/v1/fault/impact`，请求传诊断作业编号及相同的 `task_id`、`plan_id`：

```json
{"context":"planning","request_id":"impact-001","diagnose_task_id":"tsk-...","task_id":"TS-0001","plan_id":"PLAN-0001","consider_backup_route":true}
```

服务端使用诊断时冻结的场景和该数据库方案版本；即使随后切换当前方案，已有诊断的影响分析仍对应原版本。任务或方案不一致返回 `1001`。正式结果沿用现有建议、报告和导出接口。旧诊断请求不传 `context=planning` 时保留文件方案/合成基线演示行为；诊断请求传 `task_id` 或 `plan_id` 却未传正式模式，返回 `1001`，不静默降级。影响分析按所引用诊断任务识别正式来源，兼容省略 `context` 的旧请求；新请求建议显式传 `context=planning`。正式场景 CRUD 已按冻结方案校验并存入数据库；正式鉴权、前端页面适配和真实故障数据验证均未完成。当前 ML 路未启用，融合得分不是实际准确率。

**两段任务幂等与统一只读视图（2026-10-20）**：正式诊断及正式影响提交均须传非空 `request_id`（最多 120 字符）；两个操作使用不同编号。相同编号与相同请求体返回原 `task_id`，`data.replayed=true`；同编号不同内容或跨操作复用返回 HTTP 409 / `code=1204`，缺编号返回 HTTP 422 / `code=1001`。回执保存在数据库 `fault_task_submissions`，部署前须执行 Alembic `0009`。回执不会让进程重启时未完成的算法线程自动恢复；运行记录不可用时，统一查询返回 `FAILED` 与原因，须使用新 `request_id` 重新提交。

前端先 `POST /fault/diagnose`，轮询 `GET /fault/tasks/{task_id}` 至诊断成功，再以该任务编号调用 `POST /fault/impact` 并轮询影响任务。`GET /api/v1/fault/analyses/{diagnose_task_id}?task_id=TS-0001&impact_task_id=tsk-...` 为正式模式统一只读接口；诊断完成但未提交影响时可省略 `impact_task_id`。`data` 返回 `state`（`PENDING`、`RUNNING`、`DIAGNOSIS_READY`、`SUCCESS`、`FAILED`、`CANCELLED`）、`progress`（0～1）、`phases[]`、`diagnosis_ready`、`impact_ready`、`report_ready`、`error`，以及冻结的 `scenario`、`source`、可用阶段的 `diagnosis`、`impact`、`suggestions`。仅两段均成功时 `report` 非空，包含场景、诊断、影响和建议。查询会校验规划任务及两段任务关联；任务不属于该规划任务返回 HTTP 404 / `2001`，影响任务不属于该诊断返回 HTTP 409 / `1204`。该返回值为后端页面数据契约，当前前端 `DiagnosisRunView` 尚需适配，不能将其视作已完成页面实联。

```json
          {"source": "KG", "fault_type": "HW_FAILURE", "confidence": 0.85,

                        "triple_ids": ["KG-0231","KG-0788"]}},
          {"source": "ML", "fault_type": "HW_FAILURE", "confidence": 0.86,
           "evidence": {"model": "xgboost_v1", "top_features":
                        [{"name":"device_selftest","contribution":0.41},
                         {"name":"snr_db","contribution":0.19}]}}
        ],
        "candidates": [

          {"fault_type": "SW_CONFIG",  "confidence": 0.08}
        ]
      }
    ]

```

关键约定：

- `fusion_mode` 取 `THREE_WAY` 或 **`TWO_WAY_DEGRADED`**。ML 路的历史案例量未达启用门限时自动降级为规则+图谱两路，**前端必须把降级状态显示出来**（SR-5.2 d/扩展流 1 明确要求"在结果中标注当前融合路数"）

- `fused.confidence < confidence_threshold` 时 `need_manual_review = true`，前端提示人工研判（扩展流 3）
- `branches[].evidence` 是**判定依据**，前端做展开查看（SR-5.2 主事件流 6）。三路的 evidence 结构不同，前端按 `source` 分别渲染

### 数据库已保存方案历史（2026-10-23 增量）

`GET /api/v1/plan/saved-plans?context=planning&page=1&page_size=10&state=SAVED&search=...` 仅在 `FRONTEND_INTEGRATION_DEMO=1` 时开放，读取当前配置数据库中的已保存方案；不读取旧算法 JSON 文件或前端内置快照，不生成新的规划结果。

- `context` 必填，仅 `planning`；`page` 为从 1 开始的整数；`page_size` 取 5/10/20/50。
- `search` 可省略，最多 120 字，不接受控制字符；去除首尾空白后按保存名称、方案编号、任务编号或作业编号进行字面包含查询，`%` 和 `_` 不作为通配符。
- `state` 可省略表示全部，只接受 `SAVED`、`REFERENCE`、`CONFIRMED`。`REFERENCE` 表示未达标的已保存方案，不表示资料缺失的旧演示快照。
- 响应包络 `data` 为 `items/total/page/page_size/data_origin`，来源固定 `SYNTHETIC_INTEGRATION`；每项仅含 `plan_id/task_id/name/version/state/current/source_changed/saved_at`，不返回完整输入、拓扑或结果 JSON。
- 按保存时间倒序、方案编号倒序稳定分页；空目录、无匹配或越过末页返回空数组，不注入演示数据。
- `source_changed` 按当前资源版本判断，与既有详情口径一致；`current` 仅在当前方案指针指向该已确认版本且资源未变化时为真。任务条件适用性仍由打开后的完整方案流程检查。
- 未启用联调模式返回 HTTP 401 / `1101`；参数非法为 422 / `1001`；数据库未配置或操作失败分别为 503 / `5001`、`5002`。本接口没有写入、幂等回执或迁移，不代表正式多用户的数据隔离已经完成。

新版历史页签为“已保存方案”，调用 `querySavedPlanningPlans`，支持查询、状态筛选和翻页。点击打开后使用所选 `task_id` 与 `plan_id` 调用已有 `GET /api/v1/plans/{id}?context=planning&task_id=...`，经任务/调整离开保护后显示完整结果；详情失败、取消和迟到请求不应用到新现场。`/planning?history=saved` 为新入口，旧 `history=references` 链接兼容进入同一数据库历史；其他查询参数组合仍按现有安全返回地址规则限制。

旧参考快照文件和接口声明保留，但新版历史页不再调用其列表、详情、对比和导出方法；这些旧 HTTP 占位不标记为本批已完成。对比、导出、确认仍使用完整方案页已有流程，未增加跨任务对比能力。

   处理。无任务参数时保留旧算法文件 JSON/CSV/XLSX 导出，不混用两类数据来源。
15. **版本化作业取消**：`DELETE /tasks/{job_id}` 的正文须含 `context=planning`、`request_id`、
   `task_id` 和 `expected_revision`。`expected_revision` 对照作业冻结的输入版本，而非任务最新版本；
   归属不符返回 `2001`，版本不符返回 `1203`，相同请求编号被不同内容复用返回 `1204`。
   运行中的作业持久化为 `CANCELLED`，相同请求重试幂等；已完成的 `SUCCESS/FAILED` 保留原状态和结果。
   HTTP 200、外层 `code=0`，`data` 为完整作业对象，`request_id` 为本次取消请求编号。取消按算法进度
   检查点协作执行，不强制终止 Python 线程；已取消终态不会被晚到的进度回调覆盖。
16. **父方案人工调整与设备级复算**：`POST /plan/sr4-flow` 同时提供 `parent_plan_id` 和
   `adjustment={schema_version:1,source_plan_id,source_snapshot_id,manual_override,manual_paths}`。
   两个数组可为空；单条 `manual_override` 须有 `device_id` 及至少一个非空的 `tx_power_dbm`、
   `antenna_height_m`，`manual_paths` 每项含 `demand_id` 和有序 `node_path`。设备编号来自父方案
   `result.configuration.devices`，来源方案、结果快照、任务条件、资源版本及 DEM/地物指纹均须一致。
   父方案原始节点、设备、链路和链路两端设备绑定写入 `planning_plans.raw_snapshot`；同一网系同频链路
   在每端共用一台物理电台，不同网系不共用，设备不足时方案按不可行处理。子方案固定该拓扑与绑定，
   按物理设备重算参数、链路余量、路由、频率、校验、干扰与指标。返回的设备参数、人工主路径须精确回显
   提交值；未绑定链路的设备调整不改变链路性能及辐射功率。设备级需求的路由端点须继续使用指定设备。
   `data.parent_plan_id` 和 `data.adjustment` 在作业查询、方案保存及回读中保留；旧父方案缺少完整绑定
   返回 HTTP 409 / `1203`，须重新运行并保存基础方案；资源或地形变化返回 HTTP 409 / `1205`。
   人工输入越界或路径在路由图中不可用时，异步作业返回 `FAILED` 和具体错误。基础部署和 NSGA-II
   搜索仍按台站级模型执行，最终方案指标及约束结论以绑定后的物理设备级闭环复算为准。
17. **规划写操作回执**：`GET /planning-operations/{request_id}?context=planning&task_id=...&kind=...`
   从现有持久化记录只读核实 `saveTask`、`submit`、`cancel`、`savePlan`、`confirm` 五种操作；
   `saveTask` 还允许 `context=gis`。`data` 固定返回 `request_id`、`task_id`、`kind`、`state`、
   `entity_id`、`message`。已持久化写入返回 `SUCCEEDED` 和对应任务、作业或方案编号；记录不存在返回
   `NOT_FOUND`、`entity_id=null`。归属、类型或场景不符返回 HTTP 409 / `1204`，不泄露实体编号。
   作业提交成功与后续算法成功是不同状态，须另查作业接口；未持久化的失败写请求不能推断为 `FAILED`。
18. **规划任务读取与预检**：`GET /task-inputs?context=planning|gis&page=1&page_size=10&search=...`
   按当前输入版本返回 `{items,total,page,page_size}`，`page_size` 仅可为 5、10、20、50，搜索任务编号及名称；
   `GET /task-inputs/{task_id}?context=...` 返回当前完整 `ApiTask`，任务不存在或场景不符返回 HTTP 404 / `2001`。
   `active_job_id` 为最近一次已持久化的规划作业编号，无记录时为 `null`。
   `POST /task-inputs/validate` 传 `context`、`task_id`、`expected_revision`、`resource_revision`、`input`，
   只读返回 `{valid,issues,task}`；`issues` 项含 `objectId`、`field`、`message`，`task` 为当前保存版本或 `null`。
   预检核对输入结构和当前节点、设备、通视引用，不执行规划；`expected_revision` 仅供调用方识别当前版本，
   最终版本冲突仍由保存接口判定。资源版本变化返回 HTTP 409 / `1205`，历史快照不被重写。

### 6.3 SR5 写入与两阶段流程

统一写入口为 `POST /fault/workbench/actions/{action}`。公共字段为 `requestId`、`baseRevision=SR5-N`；只接受对应请求模型字段。成功回执为 `{objectId,entityIds,changed,revision}`，第一项实体编号等于 `objectId`。

| action | 补充字段 | 行为 |
|---|---|---|
| `save` | `scenarioId:null|string,draft` | 新建或新增不可变版本；已归档场景不能修改 |
| `archive` | `scenarioId,archived:boolean` | 归档/恢复，不删除历史 |
| `import` | `drafts` | 同一网络的 1–20 个场景原子写入；任一无效则全部不提交 |
| `submit` | `scenarioVersionId` | 仅提交诊断阶段，返回持久化运行编号 |
| `impact` | `runId` | 诊断成功后单独提交影响阶段，使用原冻结输入 |
| `cancel` | `runId` | 取消未完整完成的运行；已完整成功拒绝取消 |
| `feedback` | `runId,feedback` | 人工确认已有症状对应的结论后生成 SR6 草稿，不直接发布 |

`draft={name,description,planId,faults}`。名称 1–80 字、描述不超过 500 字、故障 1–20 条；故障字段为 `{objectType,objectId,faultType,symptomIds,occurTime,interferenceId}`。对象类型为 NODE/DEVICE/LINK，故障类型为 HW_FAILURE/LINK_DOWN/SW_CONFIG/EMI。发生时间为带时区 ISO 时间或 `null`；对象、症状、干扰源引用须有效。

`POST /fault/workbench/validate` 提交 draft，只读校验通过返回 `[]`；失败返回 422 业务错误。`POST /fault/workbench/import-preview` 提交 `{name,planId,base64}`，返回 `{drafts,issues}`。文件不超过 5 MiB，固定九列，最多 400 条故障行；CSV 为 UTF-8，XLSX 使用 `faults` 工作表且不允许公式。预检不保存，用户确认后再提交 `import`。

```text
读取当前来源 → 选择网络 → 设置故障/导入预检 → 保存场景版本
→ POST submit → GET progress 轮询诊断成功
→ POST impact → GET progress 轮询影响成功 → GET report → 地图/明细/导出
→ 人工确认知识反馈 → SR6 草稿 → 独立审核 → 发布 → 后续诊断使用新知识
```

相同请求编号及相同参数重放原回执；同编号不同内容返回 409/1204，过期工作区返回 409/1203。读取不提交算法。运行记录、阶段进度和结果入库；进程重启后无法继续的非终态任务明确标失败，已完成报告仍可回读。未提供的影响面、传播路径不按节点位置编造。反馈字段为 `result_index,confirmed_fault_type,root_cause,fault_component,solution,diagnosis_steps`；回执 `entityIds` 同时包含运行和知识变更编号。

### 6.4 SR6 查询与四步工作流

| 方法与路径 | 参数 | 返回 |
|---|---|---|
| `GET /kg/workbench` | 无 | 分类/类型/关系目录、工作区修订和当前已发布版本、统计及能力 |
| `GET /kg/workbench/browse/search` | `versionId,categories,type,search,pageNum,pageSize` | 版本内检索摘要分页；无匹配的业务提示在 `data.code=4001`，不是 HTTP 失败 |
| `GET /kg/workbench/browse/graph` | `versionId,categories,type,search,focusId,expandedIds` | 子图、完整计数、命中编号；显示上限 100 节点/200 关系 |
| `GET /kg/workbench/browse/entity` | `versionId,entityId` | 实体、邻居和可追溯关系 |
| `GET /kg/workbench/browse/device` | `versionId,modelId` | 指定型号的设备知识 |
| `GET /kg/workbench/history/{changes|versions|logs}` | `pageNum,pageSize`；变更可选 `state` | 对应摘要分页 |
| `GET /kg/workbench/detail/{change|version}/{id}` | 无 | 指定变更或不可变版本详情 |
| `POST /kg/workbench/actions/{action}` | 下表 | 持久化操作回执及当前知识版本 |

`categories` 为逗号分隔的分类名（设备知识、网络态势知识、故障运维知识），`expandedIds` 为 JSON 数组字符串。查询与图谱展开都绑定 `versionId=KGV-N`，不能混用版本的实体或关系。

写入公共字段：`requestId,actorId,baseRevision=KG-N`。`save` 使用 `changeId:null|string,revision:null|整数,draft`；`submit/withdraw/publish` 使用 `changeId,revision`；`review` 另含 `submission,approved,opinion`；`rollback` 使用 `versionId,reason`。回执包含 `{objectId,entityId,changed,revision,currentVersionId}`，有变更时附 `change`。幂等、修订、送审批次、权限和操作者身份由后端检查。

草稿结构为 `{baseVersionId,summary,entities,relations}`，一次最多修改 100 个实体或关系。实体包含 `{id,name,category,type,description,keywords,source,attributes,modelIds}`，可选设备 `principleFlow`（2–12 步）或组网 `networkRule`（四个不同状态的判定说明与转换）。关系包含 `{id,head,tail,type,source,weight}`，引用须完整；`weight=null` 表示页面未提供，显示保留未知，底层兼容图引擎使用既有默认权重 1.0，不得解释成实测权重。

```text
保存草稿 DRAFT → 送审 PENDING → 独立审核 APPROVED/REJECTED
→ 通过后单独发布 PUBLISHED → 生成不可变知识版本
```

撤回回到草稿；回滚复制目标快照形成新版本，不删除后续版本、变更和审计。草稿/送审/通过均不改变诊断知识。发布只影响后续新诊断；历史运行保留提交时的知识版本和分析结果。工作原理与组网说明用于知识展示，不自动改变 SR4 数值算法。

### 6.5 持久化、下载与交付限制

Alembic 迁移新增 `0011_integration_sessions`、`0012_sr5_frontend_workspace`、`0013_sr6_frontend_metadata`。新增联调会话、SR5 工作区/运行/回执表，并在既有知识版本/变更/送审/审计记录中扩展前端内容及身份快照；不修改 SR4 算法或地形原始数据。

共享客户端仅接受 PNG，或带 `Content-Disposition: attachment` 的 JSON/PDF/DOCX/XLSX/CSV 白名单文件；空文件及超过 20 MiB 明确拒绝。JSON 错误包络保留业务码和 HTTP 状态，不能作为报告下载。SR5 预置答案、清空历史和 SR6 演示重置在真实联调中返回 `UNSUPPORTED_OPERATION`，不实现全库删除。常用失败为 422/1001（参数）、404/1002 或 2001（不存在）、409/1203（版本/状态）、409/1204（请求复用）、409/1205（来源变化）、403/1104（权限）、503/5001 或 5002（数据库）。

当前检验对象是可持久化构造联调闭环，不包括正式认证、真实状态采集、设备控制、真实故障样本或 ML 训练验收。测试桩、真实 HTTP 和真实浏览器页面验收分别登记在进度台账。

## 7. P01 资源台账导出与设备筛选

2026-10-23：本节在 collab/p1-resource 独立库及 5311 页面完成验证，合入和发布状态以进度台账为准。路径前缀 `/api/v1`。无新增表、迁移或资源版本写入；不提供 GIS/观测快照导出。

| 方法与路径 | 请求/返回 | 约束 |
|---|---|---|
| POST /resource/export/preview | 下述请求 → `{revision,data_origin,source,tables:[{kind,count}],added}` | resources.view；校验会话、X-CSRF-Token、X-Session-Id；不写数据库 |
| POST /resource/export | 相同请求 → CSV/XLSX 附件 | 再次核对当前资源版本；20 MiB 上限，不截断；错误返回 JSON 业务包络 |

```json
{
  "context": "ledger",
  "revision": "<当前资源版本>",
  "format": "csv",
  "kinds": ["devices"],
  "range": "filtered",
  "filter": {"device_class": "HF"}
}
```

format 为 csv/xlsx；kinds 为不重复的 nodes/devices/interference_sources，CSV 只允许一项。range 为 all/filtered/selected：all 禁止 filter/selected_ids；filtered 必须提供 filter 且禁止 selected_ids；selected 必须提供 1–50 个不重复 selected_ids 且禁止 filter。筛选/勾选范围的非设备表初始为空；XLSX 同时选择 nodes 时补齐选中设备的节点及父级，added 为补齐数，不擅自添加未选择工作表。预检是只读提示，不是版本锁或授权令牌。

filter 支持 search、device_class=HF/VUHF、status=NORMAL/FAULT/OFFLINE/UNKNOWN、availability=ACTIVE/OFF_SHELF/UNKNOWN、alert=YES/NO/UNKNOWN、mobility、node_role、relay_capable，以及 frequency={mode:ALL/MODEL/DEVICE,presence:ALL/PRESENT/MISSING,min_khz:null|有限非负数,max_khz:null|有限非负数}。只有 DEVICE 允许非 ALL 的 presence，ALL 或 MISSING 不允许隐藏频率范围；型号频段按区间相交匹配，设备频率按已保存配置匹配，缺失状态不当正常。search 匹配设备编号、型号名、所属节点名。

GET /resource/devices 保留 context/revision/page/page_size/search/node_id/availability，补齐上述筛选（frequency 展平为 frequency_mode/frequency_presence/min_khz/max_khz）和 sort=id/name/status/workFreqKhz、order=asc/desc。完整集合先筛选排序再分页，空排序值在最后，同值按 ID 稳定排序。page_size 为 5/10/20/50；重复、未知参数或非法组合返回 422/1001，不静默忽略。ledger 场景核验 resources.view。

CSV 为无 BOM UTF-8、固定表头，空值为空、布尔为 true/false，公式前缀文本采用 `~rp~` 加 JSON 字符串（沿用前端原格式）；XLSX 数字/布尔保留类型，文本不作为公式。附件名含 synthetic 和资源版本，XLSX 说明表含版本、来源、哈希及“非生产、非实测”；响应带 X-Resource-Revision、X-Data-Origin、no-store、nosniff。

常见失败：422/1001 参数无效、404/1002 勾选设备不存在、409/1205 版本已变化、401/1101 未开启联调、403/1104 权限、403/1105 CSRF、409/1106 会话变化、503/5001 配置、503/5002 存储或数据损坏、503/5003 非数据库模式或未初始化；超文件上限为 413/1001。不返回部分成功文件，不在导出过程中改原件、资源版本或回执。
