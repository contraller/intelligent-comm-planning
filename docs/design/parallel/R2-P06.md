## 4. M1 接口、持久化与页面状态

复用路径 `/api/v1/device-configurations` 下 GET `/context`、POST `/validate`、POST 根路径、GET `/history`、GET `/{request_id}`，请求响应保持首批 a1 严格契约。context 查询为 context=ledger/device_id/revision；validate 输入 schema_version/context/base_revision/device_id/model_id/values；提交另加 request_id；values 仅 tx_power_dbm/work_freq_khz。频率、功率、型号和在架约束全部由服务端复核。

- UI 导航上下文可为 ledger/gis，wire 仍为 ledger，写入锚定当前已保存资源版本。GIS 冻结方案引用不等于当前资源；不匹配时只读详情/历史，不偷偷用最新设备替换冻结设备。
- 只显示“系统受理”“未下发”“执行未知”；不出现模拟下发进度、失败重试教学场景或成功执行值。模式/端口显示“协议待确认”，不提供可提交选择器。
- 读取、表单就绪、校验中、校验拒绝、可提交、提交中、受理、结果不明、来源过期、无权限、历史空页/读取失败分别建状态；字段修改立即清除校验有效标记。
- 每个 HTTP 方法保留发起时副本；新增可选传输 options `{signal?: AbortSignal}`，不把 signal 写入 wire。切换设备/资源/账号/离页会取消读取并提升代次，迟到响应不能应用。提交已经发出后终止等待不代表服务端取消。
- 提交前按 account_id 隔离保留 request_id、请求内容与摘要至本模块专用待核实存储，不存 Cookie/CSRF/密码。POST 超时先 GET 原号核实；仅服务明确 404 后允许同号同内容重发或放弃本地未受理草稿，不换新号自动提交。
- 服务端幂等及不可变回执继续复用 0017；历史不被刷新、表单重置或切换账号物理清空。历史分页不混入其他账号配置回执。
- M1 不增业务 API 或数据库表。已有错误码、权限和来源语义保留；旧首批证据不冒充本轮页面验证。

## 5. M2 状态快照精确契约建议

以下是提交父会话审查的内部契约，不是已存在接口。前缀 `/api/v1/device-status`，schema_version=`device-status-snapshot-a1`，context=ledger；编号复用严格 Identifier，request_id 使用路径安全编号并排除静态保留路径。额外字段、重复查询参数、非有限数值、无时区时间均拒绝。

### 输入与响应对象

- Import：`{schema_version,context,request_id,base_revision,data_origin:"SYNTHETIC_INTEGRATION",source_label,provenance_note,records}`。records 数量 1–1000，批内 device_id 不重复；超限 422/1001，不拆批后部分成功。
- Record：`{device_id,node_id,model_id,observed_at,status,alert,unknown_reasons}`。status 为 NORMAL/FAULT/OFFLINE/null，alert 为 boolean/null，observed_at 为带时区 RFC3339/null；时间规范到 UTC 但保留原始输入记录供追溯。任何未知字段须给非空原因，不能省略后补正常。
- 设备/节点/型号必须在同一 base_revision 中对应；允许保留在架或下架设备的构造历史状态，availability 只作为冻结资源字段展示，绝不由 OFF_SHELF 推成 OFFLINE。状态记录不能修改上下架、物理参数或资源版本。
- Header：`{schema_version,snapshot_id,snapshot_revision,content_hash,resource_revision,resource_content_hash,data_origin,source_label,provenance_note,imported_at,actor_id,total,counts,first_observed_at,last_observed_at}`。snapshot_id 为 DSS- 加 32 位十六进制 UUID，snapshot_revision 为 device-status- 加完整 SHA-256，imported_at 为独立服务端入库时间。
- Item：Record 加冻结的 `availability`。counts 精确为 `{NORMAL,FAULT,OFFLINE,UNKNOWN,total}`，UNKNOWN 只统计 status=null；没有已知采集时间时 first/last_observed_at 都为 null。汇总只描述输入构造记录，不推断真实在线。
- Receipt：`{schema_version,request_id,snapshot_id,snapshot_revision,resource_revision,imported_at,total,content_hash,data_origin}`。snapshot/detail/receipt 均不得由 GET 创建。
- Page：`{schema_version,items,total,page,page_size}`，page>=1、page_size=1–100 默认20；固定 `imported_at DESC,snapshot_id DESC` 或设备记录 `device_id ASC` 稳定排序。数据类型、页码、重复 ID、版本与设备关联在前后端都严格检查。

| 方法/完整路径 | 请求 | 成功 data / 权限 |
|---|---|---|
| POST `/api/v1/device-status/imports` | Import | Receipt；resources.view + 建议专项 resources.device.status.import，写请求 CSRF |
| GET `/api/v1/device-status/imports/{request_id}` | context=ledger | Receipt；当前 actor 自己的幂等回执，resources.view |
| GET `/api/v1/device-status/snapshots` | context，resource_revision 可选，page/page_size | Page<Header>；resources.view，当前项目已授权可读快照 |
| GET `/api/v1/device-status/snapshots/{snapshot_id}` | context，snapshot_revision 必填 | Header；resources.view，不与当前资源自动合并 |
| GET `/api/v1/device-status/snapshots/{snapshot_id}/devices` | context，snapshot_revision，device_id/status_filter 可选，page/page_size | Page<Item> + snapshot_id/snapshot_revision/resource_revision；status_filter=ALL/NORMAL/FAULT/OFFLINE/UNKNOWN，按快照全量服务端筛选 |

状态导入由用户显式选择构造 JSON 文件或粘贴原始构造记录并确认来源；浏览器只解析/显示错误，不计算状态结论。原资料没有采集时间时提交 null 与原因，不能用当前时间、资源版本时间或文件 mtime 冒充。HTTP 失败不自动生成默认批次。状态筛选只作用于明确选定快照，不是全库实时监控。

持久化建议 3 表：`device_status_snapshots`（头/来源/资源身份/原始构造输入摘要）、`device_status_records`（snapshot_id+device_id 唯一、冻结设备引用/状态/时间/原因）、`device_status_import_operations`（request_id 唯一、actor_id、请求摘要、冻结 Receipt）。所有记录不可变；索引覆盖快照列表、快照内状态/设备筛选。Base metadata 注册、SQL 约束/不可变触发器与正式迁移由主会话统一分配，不抢 0019 起编号、不改旧迁移。

导入首次提交在同一 SQLite 写事务内固定资源指针、校验全部引用再原子插入头/行/回执。并发资源换版返回 1205，不接受预检缓存；同 request_id/actor/规范化内容重放原回执，不同内容或身份为 1206。规范摘要覆盖来源、base_revision、原始采集时间与完整记录，不包含服务器 imported_at 或会话令牌。失败无部分批次。POST 是有限同步事务，不制造后台进度/取消接口；中断等待后按原号核实。

状态快照可由同项目具有 resources.view 的 P07 流程核验引用，但导入幂等回执仍按 actor 隔离。明确选择历史快照后保留其 resource_revision；需要当前资源投影时必须核对一致，不静默套用另一版设备。

## 6. M3 资源追溯与恢复候选

候选前缀 `/api/v1/device-traces`，schema_version=`device-trace-a1`，context=ledger。仅读现有资源底座，不写资源表、不新建历史表；配置历史调用 M1 原接口，状态历史调用 M2，不合成“配置已生效”。

| 方法/完整路径 | 请求 | 成功 data |
|---|---|---|
| GET `/api/v1/device-traces/{device_id}/history` | context，resource_revision 必填，page/page_size | Page<TraceSummary>；截至指定已存在资源版本的该设备实际变更摘要与独立基线标识 |
| GET `/api/v1/device-traces/{device_id}/operations/{request_id}` | context，resource_revision | TraceDetail；核对底座回执确实涉及该设备，不能仅凭全局 request_id 读取其他设备 |
| POST `/api/v1/device-traces/{device_id}/restore-preview` | `{schema_version,context,base_revision,source_revision,source_request_id}` | RestoreProposal；只读分析，要求 resources.view/resources.device.edit 与 CSRF；不产生业务回执/资源版本 |

TraceSummary 精确为 `{request_id,device_id,kind,base_revision,revision,created_at,actor_id,changed,changed_fields,data_origin}`；kind=RESOURCE_CHANGE/RETAINED_BASELINE。保留基线的 request_id/actor_id 为 null、changed=false，不为基线生成操作编号；底座未记操作者时保留未知原因，不联查当前用户名冒充旧快照。基线不是人为修改，其 created_at 明确为入库留存时间。TraceDetail 加 `{before,after,diffs,source_files}`，before/after 限设备已有字段，diffs 为 field/before/after/known；缺失值为 null，不填造端口/模式。

RestoreProposal 精确为 `{device_id,base_revision,source_revision,source_request_id,model_id,compatible,changes,patch,blocked_fields,warnings}`；保留基线的 source_request_id 允许 null，此时只按实际 source_revision 核验设备，不构造操作回执；非空编号必须核对对应设备与版本。patch 只允许 tx_power_dbm/work_freq_khz/antenna_height_m，按当前设备型号重新核验。跨型号、当前已下架、来源不存在、损坏、无已知可恢复参数均不给可提交候选；availability、端口、模式、status、alert、观测时间列入 blocked_fields，不借恢复修改。当前版本冲突 1205，关联/型号不兼容 1203。

确认候选仅发给宿主，不等于已保存。P01 按当前 base_revision 再校验、分配新的幂等 request_id、经统一资源底座生成新版本/回执。只有真实保存回执后页面才显示“已保存”；参数恢复不自动启用设备，不恢复旧方案有效性。P06 不调用 SQL 更新当前指针、不提供 restore 写接口，不伪造保存成功。若 P01 缺少所需写入口，此项保持明确“候选可审查，保存待集成”，不能计整条恢复闭环完成。
